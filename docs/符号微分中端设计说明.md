# Pikachu2 符号微分中端：设计、实现与重启说明

## 1. 文档定位

本文说明 Pikachu2 的标量符号表达式层，以及它与外层张量计算图自动微分之间的接口。它不是按类名罗列 API 的参考手册，而是一份面向重新开发的语义说明和源码考古记录。

本文采用以下标记区分信息的可信程度：

- **已确认**：可以由当前源码直接确认的行为；
- **设计解释**：结合代码结构和项目历史，对设计目的作出的解释；
- **未完成或待验证**：存在接口、残留实现或明显意图，但当前不能视作可用能力；
- **已知风险**：实现可能错误、依赖未声明不变量，或数学变换在部分定义域内不成立。

项目整体的历史、优缺点和重启路线见《[重启说明](重启说明.md)》。本文只深入符号微分中端。

## 2. 为什么需要符号层

Pikachu2 最初服务于 PIP NN PES。大型 PIP 可能包含十万到百万量级的单项式；它在计算结构上是一个巨大的标量代数程序，而不是少量粗粒度张量算子的组合。

将每个标量加法、乘法和幂都展开成外层张量图节点，会造成：

- 巨量图节点与边；
- 图构造、遍历和变换开销；
- 大量本可留在寄存器中的张量中间值；
- 后端难以重新识别有意义的融合范围；
- 对导数图再次求导时，图规模继续快速膨胀。

反过来，如果把整个 PIP 封装成一个完全不透明的外部算子，外层自动微分又无法穿过它。

Pikachu2 的解决思路是在张量图内部放置一个**可微的符号超级节点**：

```text
外层：张量图、参数、指标、缩并、JVP/VJP
                       │
                       │ 非线性节点持有
                       ▼
内层：标量表达式 DAG、符号微分、化简、顺序指令
```

这个结构具有“由表示方式产生的算子融合”：符号表达式内部的临时量不会自动成为外层张量；对超级节点求导时，结果仍是符号表达式，可以继续化简并作为一个整体核输出。

PIP 是这项设计的需求来源和压力测试，而不是功能边界。原则上，任何足够大、值得作为整体处理的标量非线性程序都可以进入这一层；短表达式则没有必要绕过普通张量图自动微分。

## 3. 当前代码中存在的三代表示

符号目录中存在多代相近实现，这是阅读代码时最容易混淆的地方。

| 代际 | 主要类型 | 图容器 | 当前判断 |
| --- | --- | --- | --- |
| 早期原型 | `Activation` | `graph2<ActivationVortex>` | 独立原型，包含早期前向微分和两个化简 pass |
| 中间版本 | `expression`、`activation`、`manifold`、`manifolds` | `graph2<node>` | 保留了反向微分、高阶实验和 manifold 组织方式，但不是当前张量节点的主要符号表示 |
| 较新版本 | `Expres`、`ActivFunc`、`MonoFunc`、`DiFunc` | `graph<Expres::node>`，节点继承 `vortex` | 当前张量非线性节点实际使用的路径；重启时应以此为主要语义来源 |

`expression` 与 `Expres` 的大部分算法是两代相似实现，函数名称甚至基本平行。本文除非明确说明，所说的“表达式”均指较新的 `Expres`。

重启时不应把三代代码原样迁移。合理做法是从 `Expres` 路径提取经过测试的语义，把旧版本仅作为历史参考或测试素材。

## 4. 标量表达式 IR

### 4.1 节点类型

`Expres` 使用一个有向无环图 `formula` 保存表达式。每个 `Expres::node` 有六种类型：

| 类型 | 含义 | 关键字段 | 入度 |
| --- | --- | --- | --- |
| `_LeafX_` | 输入标量 | `src1` 为输入组，`src2` 为组内分量 | 0 |
| `_LeafPara_` | 参数标量 | 当前路径主要使用 `src2` 作为展平参数编号 | 0 |
| `_LeafConst_` | 常数 | `FuncConst Fc` | 0 |
| `_Operation_` | `+ - * /` | `Code = operation` | 2 |
| `_Funct_` | `sin cos exp ln sqrt minus` | `Code = function` | 1 |
| `_Funct2_` | 当前只有 `pow` | `Code = function2` | 2 |

节点对象保存操作种类和叶节点元数据，实际父子关系由图容器维护。`node::In(0)`、`In(1)` 取得操作数，`site()` 返回节点在图容器中的位置。

### 4.2 表达式级元数据

`Expres` 还保存：

- `output`：一组输出节点指针；
- `InputDim`：每个输入组的标量分量数；
- `ParameterCount`：展平后的参数数量；
- 每个节点上的 `Output` 标志：用于打印、代码生成和图重写时维护输出身份。

一个表达式可以多输入、多参数、多输出。它仍然是**标量操作 DAG**：所谓向量输入只是若干 `_LeafX_` 节点共享一个输入组编号，而不是 IR 中存在向量算子。

### 4.3 必须保持的不变量

当前实现依赖但没有由类型系统完整保证的不变量包括：

1. 每个输出指针必须属于当前 `formula`；
2. `Output == true` 的节点应当与 `output` 数组一致；
3. 运算和二元函数必须恰有两个有序输入，一元函数必须恰有一个输入；
4. 图必须无环，拓扑序必须使操作数先于使用者；
5. `site()` 在节点存活期间必须能安全索引相应的 label 数组；
6. `_LeafX_` 的 `(src1, src2)` 必须落在 `InputDim` 描述的范围内；
7. `_LeafPara_` 的参数编号必须小于 `ParameterCount`；
8. 图重写后，所有入边、出边、输出指针和节点有效性必须同步更新。

这些约束应当成为未来新 IR 的显式验证函数，而不应继续依靠调用顺序和约定。

### 4.4 常数表示

`FuncConst` 区分整数常数、实数常数和内部的 NaN 状态。两个整数做可整除的除法时仍保存为整数，否则转为实数。常量折叠直接调用 `sin/cos/exp/ln/sqrt/pow` 等数值函数。

这一设计可以保留 `0`、`1`、小整数幂等精确模式，方便化简，但也带来几项风险：

- 实数是否为整数通过精确比较判断；
- 整数运算没有溢出检查；
- `ln` 的非法定义域会抛出动态分配的字典异常；
- `sqrt` 和 `pow` 的定义域处理不一致；
- `isZero/isOne` 没有先排除 `IfNan`，而 `nan()` 又把数值字段清零，NaN 可能被后续规则误认成零；
- NaN 与代数化简之间没有一套明确的语义策略。

## 5. 表达式的生命周期

当前数据流可以概括为：

```text
DSL/内部构造器
    │
    ▼
Expres 标量 DAG
    │
    ├── differetial(...)   生成一个指定分量的前向符号导数
    ├── backward(...)      从一个输出反向传播伴随表达式
    ├── Simplify()         化简并删除不可达节点
    └── PrintForward...    降低为 VISA1 顺序程序
                             │
                             ▼
                      解释执行/未来静态后端
```

`copy(source, OutNo)` 和 `ShrinkOutput(victim)` 可以抽取单个输出所依赖的子图。遍历通常先从输出向后标记活跃节点，再在拓扑序上处理。

一个重要实现特点是：微分并不建立完全独立的“导数图对象”。`Expres::differetial` 会把新导数节点追加到同一个 `formula`，然后将 `output` 改指向导数节点。原始 primal 节点如果被导数公式引用便继续存活，否则可以由死代码删除清除。这使得对同一对象反复调用微分自然产生高阶导数，但也使缓存、所有权和图不变量更难管理。

## 6. 前向符号微分

### 6.1 当前函数实际计算什么

`Expres::differetial(X1, X2, Input)` 选择一个独立标量：

- `Input == true` 时选择输入 `x[X1][X2]`；
- `Input == false` 时选择参数分量；
- 被选中的叶节点切向量为 `1`，其他输入、参数和常数的切向量为 `0`。

因此它当前生成的是一个**坐标偏导数**，不是接收任意切向量的通用 JVP。向量输入的完整 Jacobian 通过复制表达式并对每个输入分量分别微分得到。

算法先从所有输出标记活跃子图，取得正向拓扑序，然后为每个原节点建立导数节点 `label[site]`，最后把每个原输出替换为对应导数输出。

### 6.2 局部规则

令 `L'`、`R'` 表示当前所选方向下的导数：

| 原表达式 | 生成的导数 |
| --- | --- |
| `L + R` | `L' + R'` |
| `L - R` | `L' - R'` |
| `L * R` | `L' * R + L * R'` |
| `L / R` | `(L' * R - L * R') / (R * R)` |
| `sin(L)` | `L' * cos(L)` |
| `cos(L)` | `-(L' * sin(L))` |
| `exp(L)` | `L' * exp(L)`，直接复用原节点 |
| `ln(L)` | `L' / L` |
| `sqrt(L)` | `L' / (2 * sqrt(L))` |
| `-L` | `-L'` |
| `pow(L,R)` | `R' * ln(L) * L^R + L' * R * L^(R-1)` |

这些规则以构造普通表达式节点的方式实现，因此生成的导数可以再次微分和化简。

### 6.3 规模行为

对一个指定标量分量做一次前向微分，遍历原活跃图一次，但乘法、除法和 `pow` 会为每个原节点追加多个导数节点。对 `n` 维输入生成完整一阶导数时，`MonoFunc`/`DiFunc` 会复制表达式 `n` 次；高阶导数继续把 `cluster` 的数量乘以相应输入或参数维数。

所以当前实现更接近“枚举所有坐标偏导并物化导数张量”，而不是通过一个切向量一次计算 JVP。它满足小维度下的实现直观性，但对于高维、高阶问题，组合数量会成为首要规模限制。

## 7. 反向符号微分

### 7.1 基本过程

`Expres::backward` 从一个指定输出出发取得反向拓扑序，为输出建立种子，然后把每个节点收到的伴随表达式保存在 `label[site]` 中。

种子有两种形式：

- `ExternOutput == false`：使用常数 `1`，即普通标量输出反传；
- `ExternOutput == true`：建立一个新的 `_LeafX_` 输入组作为外部余切种子，用于表达 VJP 或多输出组合。

当同一个原节点从多条路径收到贡献时，`BackAccumulate` 显式创建加法节点。这一点保留了完整符号结构，但如果不及时做共享和化简，反向图可能迅速膨胀。

### 7.2 局部规则

令上游伴随为 `g`：

| 原表达式 | 传播到左输入 | 传播到右输入 |
| --- | --- | --- |
| `L + R` | `g` | `g` |
| `L - R` | `g` | `-g` |
| `L * R` | `g * R` | `L * g` |
| `L / R` | `g / R` | `-(g * L) / R²` |
| `pow(L,R)` | `g * R * L^(R-1)` | `g * L^R * ln(L)` |

一元函数按 `g * f'(L)` 传播，多个贡献再以加法合并。

`ParameterBackward(No)` 对一个输出执行带外部种子的反传，然后把表达式输出改为各参数叶节点的伴随表达式。它承担的是“从选定输出到全部参数”的反向程序构造，而不是一个通用、纯函数式的 VJP API。

### 7.3 已确认的正确性风险与修复状态

- 较新 `Expres` 的反向 `cos` 规则曾构造 `-cos(x)` 而不是 `-sin(x)`；现已修正，并由带 site 空洞的参数反传数值测试覆盖。
- `pow(L,R)` 对指数求导包含 `ln(L)`，隐含 `L > 0`。当 `R'` 实际为零而 `L < 0` 时，当前 eager 程序仍可能计算 `0 * ln(L)` 并产生 NaN；常整数指数的有效导数因此也可能被破坏。
- `backward` 曾按选中序列长度分配 label，却用全图 `site()` 索引；现已改为按公式节点总数分配，并加入稀疏 site 回归测试。
- 反向微分会继续向原图追加节点，当前没有统一的事务性回滚或失败后图一致性保证。

## 8. 高阶导数如何形成

项目没有为每一种 Hessian 或混合导数建立独立代数系统，而是组合已有图变换：

- 对当前输出再次调用前向微分，得到更高阶坐标偏导；
- 先反向得到参数梯度表达式，再对它做前向微分，可以形成 Hessian-vector 类结构；
- 在外层张量图中，对已经生成的导数节点继续执行 forward/backward，形成输入与参数之间的混合导数。

在 PES 场景中，核心链路是：

```text
E(R, θ)
    │ 对坐标 R 微分
    ▼
F(R, θ) = -∂E/∂R
    │ 构造包含力标签的损失
    ▼
L(F, F_label)
    │ 对参数 θ 微分
    ▼
∂L/∂θ，其中包含 ∂²E/(∂R∂θ)
```

这解释了项目为什么同时实现前向和反向图变换。所谓“平等处理”最有价值的含义不是 API 对称，而是两种模式生成的结果仍能进入同一套表示并继续微分。

不过，当前代码能构造这些图不等于数值语义已经闭合。必须用有限差分或 JAX 对能量、力和力损失参数梯度逐层验证。

## 9. `MonoFunc` 与 `DiFunc`：从表达式到符号核

### 9.1 `MonoFunc`

`MonoFunc` 表示只有普通输入、没有独立参数输入的符号核。它记录：

- 原输出数量 `OutputDim`；
- 展平输入数量 `InputDim`；
- 每阶显式导数维度 `dims`；
- 当前导数阶数 `order`；
- 保存实际表达式的 `cluster`。

构建时，若表达式节点数超过 `OutputFusionLimit`（当前为 1024），或只有一个输出，则保留一个包含全部输出的表达式；否则把每个输出拆成独立表达式并化简。这个策略说明 `OutputFusion` 实际控制“多输出是否保持在一个符号核中”。

对非标量输入微分时，每个旧 cluster 被复制 `InputDim` 次，分别对每个输入分量求导；`dims` 追加一个输入维度。标量输入不增加显式大小为 1 的维度。

### 9.2 `DiFunc`

`DiFunc` 进一步区分普通输入和参数输入，并用 `diffInfor` 记录每一阶导数是对输入还是对参数取得。理论上它可以表示诸如：

```text
output × input × parameter × input
```

这样的混合高阶导数分量排列。每次 `differential(true)` 对输入求导，每次 `differential(false)` 对参数求导；`cluster` 数量按对应维数扩张。

### 9.3 `DiFunc` 的修复状态与剩余验证边界

本轮修复了三个确定性问题：标量参数微分误选输入叶节点、非融合构建误把“抽取第 `i` 个输出”写成“对第 `i` 个输入求导”，以及 `copy` 未分配和复制 `original`。`copy` 与 `build` 现在也会先清理目标对象，避免复用实例时泄漏旧表达式或混入旧状态。

Test063 已覆盖标量参数梯度、多输出拆分、复制到非空目标以及重复 build。多维输入/参数交错的高阶组合仍未形成完整数值矩阵，因此不能把 `DiFunc` 的所有混合高阶排列视作已验证能力。

## 10. 表达式化简 Pass

### 10.1 当前通用路径实际启用的管线

`Expres::Simplify()` 当前循环执行：

```text
Simplify02 → Simplify01 → Simplify03
                 重复至不再变化
                         ↓
                    Simplify05
```

由于代码使用 `changed = changed || pass()`，C++ 的短路求值会在某个 pass 返回 true 后跳过本轮后续 pass。下一轮会从最前面重新开始。这相当于一个按优先级逐步收敛的管线，而不是每轮完整执行全部 pass。

`ActivFunc::Simplify()` 则包含 01–10 中除 05 外的多数 pass，并在固定点后执行 05。张量非线性节点经由 `MonoFunc/DiFunc` 直接调用的是 `Expres::Simplify()`，因此不能因为 04、06–10 存在于源码，就宣称它们已经参与主要符号核优化。

### 10.2 Pass 总表

| Pass | 当前作用 | 通用 `Expres` 启用 | 备注 |
| --- | --- | --- | --- |
| 01 | 代数单位元与吸收元 | 是 | `x+0`、`x-0`、`0-x`、`x*1`、`x*0`、`0/x`、`x/1` |
| 02 | 常量折叠 | 是 | 折叠四则运算与一元函数；对 `pow` 只处理零指数/零底数等特例 |
| 03 | 合并重复叶节点 | 是 | 相同常数、相同输入坐标、相同参数坐标合并；两重扫描 |
| 04 | 相同算子节点合并 | 否 | 对相同操作数的操作/一元函数做 CSE；加法和乘法考虑交换性 |
| 05 | 死代码删除 | 是 | 从输出反向标记，删除不可达节点 |
| 06 | 负号规范化 | 否 | 部分处理 `a+(-b)`、`a-(-b)`、双负号和两侧同时为负的乘除 |
| 07 | 同项简化 | 否 | `x+x→2*x`、`x-x→0`、`x/x→1` |
| 08 | 局部因式提取与约分 | 否 | 从两个乘积中提共同因子、组合常数、约去商中的共同因子 |
| 09 | 加减树重排 | 否 | 重排两层加减以聚合同项或常数，逻辑复杂且缺少独立规格 |
| 10 | 乘除约分与常数聚合 | 否 | 如 `x*(a/x)→a`，以及嵌套乘法中的常数合并 |

### 10.3 Pass 01：单位元和吸收元

实现的主要规则是：

```text
0 + x → x       x + 0 → x
0 - x → -x      x - 0 → x
0 * x → 0       x * 0 → 0
1 * x → x       x * 1 → x
0 / x → 0       x / 1 → x
```

节点替换通过 `LiftLeft/LiftRight` 完成：将被删除节点的所有使用者提升到保留的子节点，并同步迁移输出身份。

**数值风险：** 在 IEEE 浮点语义下，`0 * NaN`、`0 * Inf` 和 `0 / 0` 不能无条件化简为零。当前 pass 采用实代数语义，没有 fast-math/strict-math 模式区分。

### 10.4 Pass 02：常量折叠

当四则运算的两个输入都是常数时，节点原地变成常数叶；一元函数输入为常数时同样原地折叠。折叠后删除原入边。

`pow` 的处理并不完整：当前只把任意 `x^0` 改为 `1`，并把 `0^x` 改为 `0`。因此 `0^0`、零的负数次幂等边界会被不安全地简化。

### 10.5 Pass 03 与 04：公共子表达式

Pass 03 只合并叶节点，相当于对常数、输入坐标和参数坐标做朴素驻留。它使用两重扫描，复杂度约为 `O(N²)`。

Pass 04 才是对内部操作节点的局部 CSE：操作类型和操作数相同即合并；加法与乘法还允许左右操作数互换。一元函数按函数类型和输入相同合并。它同样是两重扫描，并且没有覆盖 `pow`。更重要的是，它不在通用 `Expres::Simplify()` 中启用。

### 10.6 Pass 05：活跃子图裁剪

Pass 05 从所有输出向输入方向遍历，删除不在任何输出依赖链上的节点。由于微分会把新节点追加到原图并替换输出，这个 pass 对控制历史 primal 和中间导数残留非常重要。

当前 `Simplify()` 的返回值主要由固定点循环轮数决定；如果只有 Pass 05 删除了节点，返回值不一定准确反映“图发生过变化”。因此调用者不应依赖该返回值作为严格的变更标志。

### 10.7 Pass 06–10：实验性代数重写

这些 pass 体现了继续优化导数表达式的方向，但目前更接近实验代码：

- 部分分支为空；
- 存在未使用变量和复杂布尔下标逻辑；
- 没有看到覆盖全部符号组合的测试；
- 多项重写依赖 `x/x=1` 或因子约分，忽略零点和 NaN；
- 重排加减与乘法会改变浮点舍入顺序；
- 某些规则可能先增加节点，是否整体获益没有代价模型。

重启时不应直接照搬。每条规则应先写成“匹配模式 → 替换模式 → 前置条件 → 浮点模式 → 测试”，再进入 pass 管线。

## 11. VISA1：从 DAG 到顺序标量程序

`VISA1` 是一个很小的虚拟指令集，包含：

| 指令 | 含义 |
| --- | --- |
| `_ld_` | 从输入、参数或常量池加载到虚拟寄存器 |
| `_op_` | 二元四则运算 |
| `_func_` | 一元函数 |
| `_func2_` | 二元函数，目前为 `pow` |
| `_st_` | 将寄存器写入输出 |

虚拟寄存器 0 被保留不用。`FreeReg` 是空闲寄存器栈；表达式图通过每个节点剩余使用次数决定何时归还寄存器。

有两种 lowering：

- `PrintForwardMiniOp`：每个叶节点和内部节点按拓扑序生成一次，优先减少重复加载/操作；
- `PrintForwardMiniReg`：叶节点在使用点加载并尽快释放，可能重复加载，意图降低同时存活的寄存器数。

`VISA1::compute` 提供解释执行器：每次调用分配寄存器数组，顺序解释指令。它适合作为代码生成器的参考语义，不适合直接承担高性能运行时。

`PrintForwardMiniReg` 曾在一元和二元函数释放叶节点寄存器时，把尚未赋值的 `label[leaf]`（通常为 0）放回空闲表，而不是刚加载得到的 `src1/src2`。该问题现已修正，并以 `sin(x) + cos(x)` 对照 `PrintForwardMiniOp` 和解析值。更复杂共享子图上的寄存器活跃性仍需要随机表达式测试。

`SymbolicCppBackend` 现在可以直接读取经过验证的 VISA1 指令和常量池，生成不依赖 Pikachu2 的 C++11 函数。MiniOp 与 MiniReg 共用同一个指令发射器；输入组、参数和输出 ABI 与解释器一致。详细接口见 `docs/符号C++后端.md`。

当前常量池仍通过线性扫描去重；对大型 PIP，常量数和程序长度增长后需要哈希驻留或在 lowering 前完成常量规范化。生成器也仍是一条指令对应一条语句，尚未恢复循环或控制宿主编译器压力。

## 12. 与张量图的接口

### 12.1 两类非线性超级节点

外层张量图用两类节点持有符号核：

- `MonoNonlinear`：一个张量输入，内部持有 `MonoFunc`；
- `DiNonlinear`：普通输入张量与参数张量两个来源，内部持有 `DiFunc`。

外层节点还保存：

- `indexSrc`：普通输入张量的指标；
- `indexPara`：参数张量的指标；
- `indexDst`：输出张量的指标；
- `function`：符号函数输出或向量化维度对应的指标；
- `x`：符号核输入分量对应的外层指标；
- `omega`：符号核参数分量对应的外层指标；
- `funcTensor`：符号函数各显式维度的大小。

### 12.2 标量输入与非标量输入

若符号核只有一个输入标量，`ScalarInput` 为真，不需要在外层显式增加一个输入分量指标。若输入有多个分量，对符号核求导会产生一个新的导数轴：

1. 找到 `x` 在 `indexSrc` 中的位置；
2. 生成一个未使用的新指标；
3. 将原 `x` 指标改名为新指标，避免与新增导数轴冲突；
4. 把旧 `x` 追加到 `function` 和 `indexDst`；
5. 把输入分量数追加到 `descriptor` 与 `funcTensor`。

参数微分对 `omega/indexPara` 执行对称操作。这里的“新指标”并不是设计核心，而是把局部 Jacobian 轴送回外层张量图的编码办法。

### 12.3 外层 JVP

非线性节点前向微分的结构是链式法则：

```text
局部符号导数核 × 输入切向量
```

`MonoNonlinear::forward` 取得符号导数节点，再建立一个 `DiLinear` 进行指标乘积/缩并。`DiNonlinear::forward` 分别构造对普通输入和参数的局部导数，与两侧切向量相乘后相加。

### 12.4 外层 VJP

反向微分则构造：

```text
上游余切 × 局部符号导数核
```

结果通过外层指标规则缩并回输入或参数的 descriptor；多个下游贡献由 `NetWork::BackAcc` 累加。

这就是两层自动微分真正衔接的位置：内层负责得到局部标量程序的偏导，外层负责把偏导张量与 tangent/cotangent 按指标组合。

### 12.5 缓存风险

`MonoNonlinear` 缓存一个 `gradient` 指针，`DiNonlinear` 分别缓存 `gradientX` 和 `gradientP`。后续请求会直接复用缓存，而请求参数还包含 `Affiliation`。当前没有看到表达式修改后的缓存失效机制，也没有证明同一局部导数节点可安全跨不同微分阶段复用。重启时应让导数缓存键显式包含 IR 版本、微分变量和必要的模式信息，或先完全取消缓存以保证正确性。

## 13. 自动融合的准确含义

“符号微分内嵌在张量微分中会自动完成算子融合”是合理描述，但需要限定：

- 它自动保留了**融合边界**，避免把内部标量操作暴露为外层张量节点；
- 内层导数仍保持在同一个标量程序 IR 中，天然适合作为单个循环体或设备核；
- 它没有自动完成循环生成、向量化、公共子表达式、寄存器分配、内存规划和 CUDA kernel 调优；
- `OutputFusionLimit = 1024` 只是当前按节点数决定多输出是否共用表达式的简单启发式，不是成熟代价模型。

因此，更准确的说法是：Pikachu2 通过分层 IR 保存融合机会，并已能把单个符号核兑现为一个静态 C++ 函数；但循环生成、外层张量图融合以及高性能 C++/CUDA 仍属于未完成后端的职责。

## 14. 对大型表达式的现实复杂度评估

当前设计适合表达大型符号核，但当前实现还不能据此推断能高效处理百万单项式。主要瓶颈包括：

- `Simplify03/04` 的两重全图扫描为 `O(N²)`；
- 每个输入或参数分量通过深拷贝表达式生成导数；
- 高阶导数的 cluster 数量按各阶维数的乘积增长；
- 反向累加直接建立加法树，没有专门的 n 元加法或稀疏聚合表示；
- 常量池去重为线性扫描；
- 图容器中存在洞、裸指针和频繁小对象分配；
- 代数重写没有 e-graph、哈希 cons、全局 CSE 或代价模型；
- 尚无针对生成源码大小和宿主编译器压力的控制策略。

但设计仍然提供了正确的优化位置。未来可在符号核内部引入：

- 构造时 hash-consing，而不是事后 `O(N²)` 合并；
- n 元加法/乘法与规范化单项式；
- 稀疏多项式专用表示和通用 DAG 之间的可逆 lowering；
- 分块微分，避免一次物化完整 Jacobian；
- 活跃性驱动的顺序程序与临时量复用；
- 按源码体积、寄存器压力和重复计算权衡的分核策略。

这些是对现有分层思想的强化，不要求恢复原有自定义前端。

## 15. 数学与浮点语义必须显式化

未来实现至少需要选择并记录两种模式之一：

### 严格浮点模式

尽量保持 IEEE 行为、NaN/Inf 和求值顺序，不执行 `0*x→0`、`x/x→1` 等可能改变特殊值行为的规则，也谨慎处理结合律和交换律重排。

### 实代数/快速模式

假定输入位于函数定义域内、分母非零、没有 NaN/Inf，并允许结合、交换、约分和吸收元简化。PES 的受控数值域可能适合此模式，但前置条件必须由调用方承诺或由验证器检查。

当前代码实质上混用了两种语义：运行时使用 IEEE `double`，优化却按实代数恒等式重写。重启时应把它变成显式编译选项，而不是隐藏假设。

## 17. 应建立的验证矩阵

在继续后端之前，建议把文档中的每条语义变成小型测试。

### 17.1 每个原语的标量测试

对 `+ - * / sin cos exp ln sqrt pow minus` 分别检查：

- primal；
- 指定方向的前向导数；
- 反向导数；
- 前向与反向结果的一致性；
- 一阶导数与中心有限差分；
- 二阶导数与有限差分或 JAX。

测试点应包括普通点和定义域边界附近，但不能用“两个实现都产生 NaN”代替语义定义。

### 17.2 图结构测试

- 多输出共享子图；
- 同一叶节点被多条路径使用；
- 图中存在已删除节点形成的 site 空洞；
- 微分后再次微分；
- 微分、化简、复制、抽取单输出的不同排列；
- 输出本身就是输入或常数；
- 某参数对输出无贡献时梯度为显式零还是空指针。

### 17.3 Pass 测试

每个 pass 至少需要：

- 一个应当重写的正例；
- 一个结构相似但不应重写的反例；
- 输出节点恰好是被替换节点的情况；
- 被替换节点有多个使用者的情况；
- strict/fast 浮点语义下的特殊值测试；
- 重复执行达到幂等固定点的测试。

### 17.4 两层集成测试

最小纵向例子应包含：

1. 一个多分量输入的符号核；
2. 一个带参数的 `DiNonlinear`；
3. 外层张量缩并；
4. 能量对坐标的力；
5. 力损失对参数的混合二阶导数；
6. 符号核 C++ 结果与解释器/解析值对照，并进一步加入全图结果与 JAX/有限差分对照。

## 18. 重启时建议保留和重写的边界

### 应保留的语义

- 标量符号核与外层张量图分层；
- 输入、参数、输出的明确区分；
- 前向和反向产生仍可微分的 IR；
- 符号局部导数与张量 JVP/VJP 的接口；
- 符号核作为静态代码生成和融合单元；
- `VISA1` 所体现的“活跃性驱动顺序程序”思想。

### 应重写的实现

- 三代重复表达式类；
- 裸指针所有权和动态分配的异常对象；
- 以裸 site 直接索引的大数组设计（当前已消除已知越界，但仍耦合全图编号）；
- 编号式、缺少规格的 Simplify pass；
- 坐标偏导深拷贝造成的组合爆炸；
- 线性扫描式 CSE 与常量池；
- 隐式的 strict/fast 数学假设；
- 符号 IR、优化器和代码生成器之间相互暴露内部状态的接口。

新的最小实现可以使用 Python 构图和标准容器。当前符号核 C++ 后端已经提供第一层可执行语义规范；迁移时应迁移本文件定义的行为、生成 ABI 和测试，而不是迁移旧类层次本身。

## 19. 最终判断

符号层不是 Pikachu2 中多余的自研组件；它正是这个项目区别于普通小型自动微分框架的核心。真正多余的是围绕它扩张出来的大量通用基础设施，以及三代没有收口的实现。

它最值得保存的思想可以浓缩为一句话：

> 将足够大的标量程序保留为张量图中的可微融合单元，在符号层生成局部导数，在张量层组合 JVP/VJP，并让结果继续参与高阶微分。

下一步不是继续增加符号规则，而是扩展数值测试以固定剩余语义，并让外层张量图调用已完成的 `Expres/VISA1` C++ 符号核，跑通能量、力和力损失参数梯度这一条纵向链路。首轮修复与后端实现记录分别见 `docs/log/2026-09-09-重启首轮修复.md` 和 `docs/log/2026-09-10-符号C++后端.md`。

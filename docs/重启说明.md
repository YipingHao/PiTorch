# Pikachu2 重启说明

## 这份文档的用途

Pikachu2 是一个没有完成的 C++ 神经网络与自动微分框架。这份文档不是给现有代码补一层漂亮的叙事，也不是承诺把原计划全部完成；它记录项目为什么会出现、真正值得保留的设计是什么、工程为什么逐渐失控，以及如果重新开发，最小而可信的路线应当是什么。

项目的代码质量和设计价值需要分开评价：它的工程实现有明显的个人项目痕迹，但问题意识并不业余。尤其在大规模符号表达式、高阶混合导数和算子融合之间建立联系，是这个项目最有价值的部分。

## 项目的来历

项目最初服务于 PIP NN PES（使用置换不变多项式的神经网络势能面）训练。PIP 在较大体系中可能包含十万到百万量级的单项式。它在数学上更像一个巨大的标量符号程序，而不是常规深度学习框架擅长处理的一串中等粒度张量算子。

如果把每个加法、乘法和幂都展开成普通计算图节点，图会极大，调度、内存、图变换和编译开销都会变得不合算；如果把整个 PIP 当成一个不可见的外部算子，框架又无法自动得到它的导数。Pikachu2 因而尝试在一个系统里同时容纳两种表示：

- 外层是张量计算图，表达网络结构、参数、张量指标和算子之间的依赖；
- 内层是标量符号表达式，表达一个非线性算子内部可能非常庞大的代数程序，并能够在这一层直接微分和化简。

另一个直接动机来自势能面的训练目标。力是能量对原子坐标的导数；一旦把力标签放进损失函数，再对模型参数训练，就会出现坐标与参数之间的混合二阶导数。项目因此没有把反向模式视作唯一的主路径，而是试图让前向微分和反向微分都成为可组合的图变换，以继续构造梯度、Jacobian、Hessian-vector product 等高阶对象。

后来，实际研究中出现了更合适的算法级解决方案，而 JAX 已足以承担当前工作流，继续维护一整套自研框架不再具有现实收益。项目便停在了前端和自动微分中端大体成形、静态执行后端与成熟图优化尚未完成的位置。

## 它真正想解决的问题

PIP 是最初的典型用例，但不是系统功能的定义。更准确的目标是：

> 允许任意“足够大、值得整体处理”的标量符号表达式作为张量图中的可微算子，并让符号层与张量层的微分能够组合。

短小表达式完全可以留给普通张量图自动微分；当一个表达式大到逐项进入张量图会产生不可接受的节点数和中间量时，才把它放入符号层。这个分层本质上提供了一种由表示方式决定的自动融合：符号表达式是一个超级节点，其内部中间值不会被强制物化成外层张量，也不会把整个标量程序炸成海量图节点。对这个超级节点求导后，导数仍然是符号程序，因而可以继续化简、公共子表达式消除并作为一个融合后的核输出。

所以，项目的核心不是某套 dummy/repeated/new index 规则，也不是“前向和反向形式上平等”本身。指标规则是为了让实现可行而设计的局部语言；双模式微分是高阶导数组合的机制。真正的主线是：

1. 用适合规模的 IR 表示问题；
2. 在符号核内部做标量程序微分；
3. 在张量图外部做算子级微分；
4. 让两层导数在边界处正确衔接；
5. 把符号核作为天然的融合与代码生成单元。

## 当前架构的理解

### 1. 自定义前端

项目包含词法、语法、上下文、变量和函数等设施，提供了一套接近 Python/数学记号的 DSL。它把用户程序转换为框架自己的对象和计算图。

### 2. 标量符号层

`Expres`、`MonoFunc`、`DiFunc`、`manifold` 等类型描述标量表达式、单输入/双输入非线性函数及其导数。表达式在这一层被复制、微分、化简，并可进一步转成类似顺序指令的 `VISA1` 表示。这一层适合容纳 PIP 或其他大型非线性代数核。

### 3. 张量图层

`NetWork` 管理张量节点和依赖关系。节点大致分为叶节点、单输入线性、双输入线性、单输入非线性和双输入非线性五类。张量指标描述输入、参数、函数维度和输出维度之间的映射；dummy、repeated、new index 等规则承担缩并、广播/保留以及微分新增维度的表达工作。

### 4. 自动微分中端

节点能够参与 forward、backward、gradient、Jacobian、Hv 等图变换。非线性节点的局部导数由内部符号表达式产生，线性节点的导数通过指标变换重建。这正是两层 IR 接合的位置，也是现有代码最值得保留并优先验证的部分。

### 5. 未完成的后端

后端目前更接近骨架：能够收集网络信息并拼接部分运行时代码，但还没有形成一个边界清晰、可独立验证的静态 C++ 代码生成器；CUDA 输出和终端级图优化也没有完成。因此，当前系统“能建图、能变换”不等于“已经是可用框架”。

## 值得保留的设计

- **两层 IR 对应两种尺度。** 巨型标量代数和张量网络不是同一种图，强行使用统一粒度未必简洁或高效。
- **融合是表示的一部分。** 符号超级节点不是在末端依赖启发式 pass 临时拼出来的，而是在建模时就保留了有意义的核边界。
- **微分可以穿过融合边界。** 内层表达式不是 opaque custom op；框架知道如何生成它对输入和参数的导数。
- **高阶导数是一等需求。** 力训练使混合二阶导数成为实际需求，而不是为了炫技添加的功能。
- **规则集中在中端。** 即便未来替换前端和图容器，符号/张量两层的微分规则仍可作为语义核心迁移。
- **静态代码生成适合科学计算部署。** 对形状稳定、算子集合有限的 PES 计算，生成简单 C++/CUDA 核具有可预测、易嵌入和低运行时开销的优势。

## 工程上的稚嫩和代价

这些问题不是否定设计，而是解释为什么一个人继续扩张项目会越来越慢。

### 手搓了过多非核心设施

项目自己实现或包办了容器、字符串/字典、图结构、词法与语法分析、上下文、错误对象、张量描述、代数运行时、构建脚本等大量基础设施。其中不少工作对验证“两层微分”没有直接贡献，却扩大了需要同时保持正确的表面积。

如果今天重做，自定义语言前端、通用容器和大部分运行时框架都不是第一阶段必需品。Python 可以直接承担用户前端与图构造；标准库容器可以取代多数自定义容器；成熟的解析、测试和构建工具可以避免重复解决通用问题。

### 抽象边界不够稳定

节点类之间通过裸指针、`friend`、共享内部状态和隐含调用顺序连接。描述符、指标数组、网络归属和缓存导数之间存在许多没有被类型系统表达的不变量。部分函数在“构造对象”“加入网络”“连边”“计算描述符”之间承担多项职责，使局部修改很容易破坏远处假设。

### 内存所有权与错误处理不统一

大量对象直接 `new`，所有权和生命周期常由图结构或调用约定隐式决定。错误有时用整数返回，有时抛出动态分配的字典指针，有时使用 `PikaError`。这种混合方式增加泄漏、重复释放、漏检错误和异常路径失真的风险。

### 存在代际重复与未收口接口

代码中能看到名称或职责接近的多代对象和接口，例如大小写不同或新旧并存的 expression/activation/network 相关实现。部分函数是空壳，部分测试是迁移后留下的占位，后端也混合了“生成代码”和“拼接现成运行时”的思路。它们说明项目在探索过程中不断改向，但旧路径没有及时删除或封装。

### 构建与可移植性较弱

源码中有依赖当前目录结构的错误相对路径、硬编码的 MKL 开关和机器路径，构建脚本也假定特定类 Unix 环境。这类问题与算法无关，却会阻止新环境首先得到一个可编译基线。

### 验证体系落后于功能复杂度

现有测试并未把关键语义压缩成小而稳定的回归用例。对自动微分系统，最需要的是每类节点的 primal、JVP、VJP 以及混合二阶导数的数值对照；没有这些护栏，指标规则中的一处下标写错或循环上界错误就可能长期潜伏。

### 优化仍然是初等和局部的

已有化简体现了正确方向，但还没有形成清晰的 pass 管线、纯 IR 不变量、代价模型和端到端基准。对于百万单项式，真正决定性能的不只是局部代数化简，还包括公共子表达式、活跃性、临时量复用、循环/缩并生成、常量布局和编译规模控制。

## 对单人开发经历的判断

这是一个典型的“研究问题正确，但工程边界太大”的项目。作者是物理化学背景的单人开发者，却同时承担了语言实现、编译器 IR、符号代数、张量图、自动微分、数值运行时和后端代码生成。任何一个模块单独都足以成为长期项目；在缺少代码生成助手和持续同行评审的时期，它们一起增长，设计与工程质量失控几乎是必然结果。

所谓“剑走偏锋”主要体现在实现路线，而不在问题本身：为了抵达一个少见但真实的计算需求，项目绕过成熟生态，自己修了一条过长的路。结果是核心思想被大量非核心代码包围，也让每次架构修正都付出高昂迁移成本。

这段历史最值得保留的经验不是“以后不要自研”，而是：先把独特语义缩成可以独立验证的内核，再让成熟工具承担外围工作。

## 建议的重启路线

### 阶段 0：先稳定现有 C++，不要立即重写

直接迁移到 Python 未必是最低成本。现有 C++ 已经包含最多、最难重建的微分规则；在缺少可执行参照时重写，容易把迁移和语义调试混为一件事。第一步应当修复明确的未定义行为和构建问题，并让当前代码得到一个可重复编译的基线。

### 阶段 1：补一个最小静态 C++ 参考后端

这个后端的目标不是性能，而是把整个系统纵向跑通。建议严格限制范围：

- CPU、`double`、静态形状、单线程；
- 按拓扑顺序执行；
- 使用朴素临时缓冲区和朴素循环；
- 把符号表达式输出为简单的顺序标量程序；
- 只生成少量清楚的函数，例如参数/输入装载与 `evaluate`；
- 暂不做 CUDA、并行、复杂内存规划、训练器和激进优化。

它应被视为“可执行语义规范”。一旦这个版本能产生正确结果，未来的 Python 前端、JAX 对照或 CUDA 后端都有明确的比较对象。

### 阶段 2：只验证一条最关键的纵向链路

优先选择一个很小但包含真实需求的模型，完成：

1. 能量前向计算；
2. 能量对坐标的导数，即守恒力；
3. 含力标签的损失；
4. 该损失对模型参数的导数，即坐标—参数混合二阶导数。

每一层都与有限差分或一个可信参考实现对照。只有这条链路通过，才能说明两层微分的核心设计真的闭合。

### 阶段 3：再迁移外围，而不是照搬旧工程

当 C++ 参考后端跑通后，可以用 Python 代码替换自定义 DSL，用成熟容器管理图，并把旧中端规则重新表达成更小、更纯的 IR 变换。建议保留的只有：

- 标量符号核 IR；
- 张量图 IR；
- 两层之间的微分接口；
- 指标语义中经过测试证明必要的部分；
- 可生成静态 C++/CUDA 的后端边界。

JAX 可以作为正确性参考和普通张量层的现成执行器。如果仍要保留大型符号核的边界，可在后续把它接成 custom primitive/custom call；不必第一天就把整套旧前端搬进 Python。

## 重启时的边界

为了避免再次失控，第一轮开发明确不做以下事情：

- 不恢复一门完整的自定义语言；
- 不追求通用动态图框架；
- 不同时开发 CPU、CUDA 和 JAX 三套成熟后端；
- 不先做复杂图优化再证明语义正确；
- 不保留仅因历史存在、却没有回归测试支撑的抽象；
- 不把 PIP 专用优化混入通用 IR 的基本正确性层。

一个合理的成功标准不是“取代 JAX”，而是：用尽可能小的代码证明大型符号核可以嵌入张量图、跨层自动微分可以正确组合，并能输出独立可运行的静态程序。达到这一点，这个项目就从一套未完成的框架，变成了一个清楚、有实验价值、也可继续演化的原型。

## 当前结论

Pikachu2 值得重启，但不值得按原来的宽度继续施工。它最有价值的资产不是自定义前端、容器或运行时，而是对计算粒度的判断：大型符号表达式应当在张量图中保持为可微的融合单元；高阶导数需要内外两层微分规则共同闭合。

因此，近期最合理的工作顺序是：修复确定性 bug，建立编译与数值回归基线，补齐最小 C++ 参考后端，跑通能量—力—力损失参数梯度，然后再决定哪些部分值得迁移到 Python/JAX，哪些部分应当永久删除。
